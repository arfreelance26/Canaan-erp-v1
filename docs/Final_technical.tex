\section{Executive Summary \& System Architecture}

Canaan ERP is a specialized, trip-centric logistics enterprise system designed specifically for container transport operations in Chennai port logistics. The platform manages the entire operational lifecycle: booking intake, vehicle and driver assignment, on-road tracking, trip-sheet reconciliation, accounts verification, and GST-compliant invoice generation, alongside fleet compliance, maintenance, tyre lifecycle management, fuel logging, staff and driver attendance, finance, and per-truck P\&L analytics.

The system is deployed as a unified four-tier ecosystem:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Backend REST API \& WebSocket Server}: Built with FastAPI (Python 3.10+), serving 205 endpoints across 21 domain routers with token-guarded authentication, optimistic locking, and real-time state broadcasts.
    \item \textbf{Relational Database}: MySQL with $\sim$40 normalized tables, document BLOB storage (\texttt{LONGBLOB} up to 25 MB), and automated startup migrations.
    \item \textbf{Web \& Desktop Frontend}: Next.js 16 (App Router) with React 19 Single Page Application, also packageable as an Electron desktop application.
    \item \textbf{Mobile Companion Application}: Flutter (iOS \& Android) Admin client providing real-time operational monitoring, offline caching, and biometric hardware security.
\end{enumerate}

\subsection{Enforcement Mechanisms}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Backend Route Guards}:
    Every business router requires a valid JWT via \texttt{Depends(get\_current\_user)}. Sensitive modules enforce strict role requirements using \texttt{require\_roles(...)} dependencies (for instance, \texttt{/finance} and \texttt{/pl-summary} require the \textit{Accounts} or \textit{Admin} role). Destructive actions like \texttt{DELETE /trips/\{id\}} require admin privileges or an active temporary edit approval token.
    
    \item \textbf{Frontend Navigation Guards}:
    The web client maintains a \texttt{ROLE\_HREFS} map in \texttt{Sidebar.tsx}. Unauthorized navigation items are omitted from the DOM. Upon login, roles without global dashboard access are redirected directly to their designated workspace (for example, Yard Supervisor to \texttt{/trips/sheet-collection}).
    
    \item \textbf{Mobile Client Gating}:
    The mobile companion application strictly restricts login to the \textit{Admin} role, which is validated client-side prior to token storage and enforced server-side on all endpoints.
\end{enumerate}

\section{Data Model \& Entity-Relationship Architecture}

The database contains $\sim$40 normalized tables across 8 logical domains. All mutable business entities implement \textbf{Optimistic Concurrency Control} through an integer \texttt{version} column and UTC timestamps (\texttt{created\_at}, \texttt{updated\_at}).

\subsection{Domain Entity Structure}

\begin{diagrambox}{Logical Data Domains}
Administration
 \-- Branch: Operating branches, halt-day fees, driver halt compensation percentage

Resource Hub
 |-- Truck: Fleet master, specifications, compliance dates, document BLOBs
 |-- Driver: KYC, licence, Aadhaar, PAN, Form-11/ESI, credentials, document BLOBs
 |-- Staff: Designation, credentials, KYC, department, login access
 |-- Customer: GSTIN, GTA status, e-invoicing, Origins, Destinations, Pricing
 \-- Vendor: Vendor master, category, GSTIN/PAN

Trip Operations
 |-- DriverAssignment: Active driver to truck pairing (one active per driver)
 |-- Trip: Central hub: status, booking, cargo, route, pricing, LR consignment note
 |-- TripClosure: Closure snapshot, halt days, driver halt compensation
 |-- TripSheet: Reconciliation, expenses, driver settlement, diesel JSON entries
 \-- TripInvoice: Tax Invoice, Bill of Supply, Transport Memo, SAC line items

Attendance & HR
 |-- DriverAttendance / StaffAttendance: Daily check-in/out logs
 |-- DriverAttendanceRemark / DriverAttendanceLateEntryLog: 2-day bypass mechanism
 \-- LeaveRequest: Leave lifecycle with approval workflow

Maintenance
 |-- MaintenanceRecord: Service records linked to trucks and trips
 |-- FuelLog: Vehicle fuel logs synced automatically from Trip Sheets
 |-- AdBlueLog / AdBlueManufacturer: AdBlue consumption and vendor rates
 |-- TyreInventory: Stock tracking, condition, retreading count and cost
 \-- TyreFitmentRecord: Odometer-tracked tyre mounting and dismounting

Finance Hub
 |-- EmiRecord: Truck financing, monthly and daily cost derivation
 |-- RecurringPayment: Fixed recurring overheads and due dates
 |-- CompensationTransaction: Driver advances, staff salary transactions
 \-- EditApprovalRequest: 1-hour time-limited edit/delete authorization

System & Audit
 |-- AuditLog: Append-only security audit log
 \-- Notification: System alerts and reminder dispatches
\end{diagrambox}

\subsection{Architectural Data Rules}

\begin{itemize}[leftmargin=*]
    \item \textbf{Decoupled Trip Hub}: The \texttt{Trip} entity holds foreign keys to \texttt{Customer}, but stores \texttt{driver\_id} and \texttt{vehicle\_id} as stable string references (\texttt{CGI-D001}, \texttt{CGI-T001}). This ensures historical trip manifests remain immutable even if driver or vehicle records are modified or archived.
    \item \textbf{Automatic Diesel Sync}: When a \texttt{TripSheet} is saved, the backend parses its embedded \texttt{diesel\_entries} JSON array and automatically creates or updates corresponding entries in \texttt{FuelLog} tagged with \texttt{source = "Trip Sheet-\{id\}"}.
    \item \textbf{Polymorphic Transactions}: \texttt{CompensationTransaction} and \texttt{LeaveRequest} handle both staff and driver records through polymorphic composite keys (\texttt{person\_type} + \texttt{person\_id}, \texttt{category} + \texttt{applicant\_id}).
\end{itemize}

\section{Core Business Workflows}

\subsection{Six-Stage Container Trip Lifecycle}

\begin{diagrambox}{Trip Pipeline Stages}
[1. ASSIGNMENT]   ==>  [2. EXECUTION]   ==>  [3. COLLECTION]
Commercial Mgr         On-Road Tracking       Yard Supervisor
(Kumar)                Status Lifecycle       (Antony)
       |                                             |
       v                                             v
[6. INVOICING]    <==  [5. VERIFY]      <==  [4. RECONCILE]
Accounts Auto          Accounts Team          Docs / Register
TM / BS / Tax          Sunder / Thanamani     (Latha, Siva)
\end{diagrambox}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Stage 1: Trip Booking \& Assignment (Commercial Manager)}:
    \begin{itemize}
        \item Container Number Validation: Regex verification requiring exactly 4 uppercase letters followed by 7 digits (\texttt{\textasciicircum[A-Z]\{4\}[0-9]\{7\}\$}) across up to 3 container slots.
        \item "Self" (CGI) Rules: Billing is locked, payment forced to Credit, invoice type set to Transport Memo (no GST), driver advances hidden, and CHA locked to "CGI".
        \item Baseline Mileage: Estimated distance (\texttt{approx\_km}) is recorded to establish the baseline for downstream variance checks.
        \item Lift-On/Off Rules: Auto-populated from customer rate cards for standard containers; manual for Open/Shifting; forced to 0 for Coastal.
    \end{itemize}

    \item \textbf{Stage 2: Trip Execution}:
    Trip status advances through: \texttt{Assigned} $\rightarrow$ \texttt{Started} $\rightarrow$ \texttt{Loaded} $\rightarrow$ \texttt{On-Transit} $\rightarrow$ \texttt{Reached} $\rightarrow$ \texttt{Unloaded} $\rightarrow$ \texttt{Completed}. Status changes emit real-time WebSocket notifications.

    \item \textbf{Stage 3: Trip Sheet Collection (Yard Supervisor)}:
    Yard supervisor collects physical trip sheets, verifies cash advances issued to drivers, records \texttt{ts\_received\_date}, and flags missing sheets if uncollected within 24 hours.

    \item \textbf{Stage 4: Trip Sheet Reconciliation (Docs Team)}:
    Docs team enters odometer readings, cargo weights, toll expenses, port pass, mamool, and fuel receipts.
    \begin{itemize}
        \item $\pm$\textbf{10\% KM Variance Alert}: If actual odometer distance deviates from \texttt{approx\_km} by more than 10\%, a mandatory remark popup blocks saving until an explanation is provided.
        \item \textbf{Diesel Synchronization}: Fuel entries auto-replicate to the vehicle's fuel maintenance log.
        \item \textbf{Flag for Re-Checking}: Preserves pending draft status without forwarding to accounts.
    \end{itemize}

    \item \textbf{Stage 5: Accounts Verification (Accounts Team)}:
    Accounts verifies freight rates, driver expenses, and net margins.
    \begin{itemize}
        \item \textbf{Approval (Tick)}: Locks reconciliation and enables invoice creation.
        \item \textbf{Rejection (Cross)}: Rejection reason is stored; trip shifts to \texttt{rejected} status and displays an alert banner on the Docs dashboard.
    \end{itemize}

    \item \textbf{Stage 6: Invoice \& LR Consignment Generation (Accounts Team)}:
    \begin{itemize}
        \item \textit{Self (CGI)}: \textbf{Transport Memo} (Freight and Halt only; no GST).
        \item \textit{Customer + GTA Registered}: \textbf{Bill of Supply} (Freight charges under RCM; no forward GST).
        \item \textit{Customer + Non-GTA}: \textbf{Tax Invoice} (Standard forward-charge GST applied).
        \item Numbering Sequences: Transport Memo (\texttt{CGI\{FY\}/TM\{nnnn\}}), Bill of Supply (\texttt{CGI\{FY\}/BS\{nnnn\}}), Tax Invoice (\texttt{CGI\{FY\}/T\{nnnn\}}).
        \item Immutable Dates: Invoice dates are locked to current IST date to prevent backdating.
        \item LR Generation: Standardized A4 Lorry Receipts (Consignment Notes) generated via client-side PDF synthesis.
    \end{itemize}
\end{enumerate}

\subsection{Edit \& Delete Approval Protocol}
Modifying sensitive records (Customers, Vendors, Bookings, Trip Sheets, Closed Trips) requires an \texttt{EditApprovalRequest}. Upon Admin approval, the backend issues an authorization token granting a strict \textbf{1-hour editing window} (\texttt{expires\_at}).

\subsection{Compliance Expiry Warning Engine}
Fleet compliance documents trigger proactive dashboard warnings:
Fitness Certificate (30 days), Permits (10 days), Road Tax (10 days), PUC and Insurance (7 days).

\section{Real-Time Synchronization \& Data Consistency}

The platform implements a \textbf{Persist $\rightarrow$ Broadcast $\rightarrow$ Refetch} consistency model across all clients.

\begin{diagrambox}{Data Consistency Workflow}
Client Action (POST / PUT / PATCH / DELETE)
                 |
                 v
     FastAPI Backend Router (DB Commit)
                 |
                 v
     Realtime Broadcast Middleware
                 |
                 v
     WebSocket Broadcast (/ws) ==> "data_changed" { resource: "trips" }
                 |
                 v
     Frontend Clients (useAutoRefresh)
                 |
                 v
     Debounced REST Re-fetch (300ms) -> UI State Updated
\end{diagrambox}

\subsection{Real-Time Pipeline Guarantees}
\begin{enumerate}[leftmargin=*]
    \item \textbf{Zero Sensitive Data over WebSocket}: The WebSocket channel emits only lightweight resource change notifications (for example: \texttt{\{"event": "data\_changed", "resource": "trips"\}}). No personal data or business records travel over the socket frame.
    \item \textbf{Authenticated Sockets}: \texttt{/ws?token=<jwt>} validates token signature, expiry, and revocation denylists upon connection. Sockets close automatically (\texttt{code 4001}) if a token expires mid-session.
    \item \textbf{Debounced Throttling}: Server-side debouncing (250ms) and client-side hook debouncing (300ms) prevent refetch storms during bulk operations.
    \item \textbf{Graceful Polling Fallback}: In environments without persistent WebSocket proxying (such as shared cPanel hosting), \texttt{useAutoRefresh} falls back to 60-second polling and tab focus refreshes.
\end{enumerate}

% SECTION 10: FULL-STACK SECURITY ARCHITECTURE
% ==============================================================================
\section{Full-Stack Security Architecture \& Hardening}

\subsection{Web \& Backend Security Controls}

\begin{diagrambox}{Backend Security Controls}
1. JWT HS256 Token Auth (12-hour expiry, unique jti, fail-closed secret)
2. Server-Side Token Revocation (Instant jti denylist on logout)
3. IP + Username Lockout (5 failed attempts -> 15 min lock; Admin reset)
4. Authenticated Document Access (Token-guarded /files/..., audit-logged)
5. Magic-Byte Upload Sniffing (File signature validation; 25 MB cap)
6. Append-Only Tamper-Evident Audit Trail (audit_logs table)
7. Constant-Time Admin Authentication (secrets.compare_digest)
8. Hardened Security Headers (CSP, X-Frame-Options: DENY, HSTS opt-in)
9. Safe Error Hygiene (Generic client errors, server-only stack traces)
\end{diagrambox}

\begin{itemize}[leftmargin=*]
    \item \textbf{Authenticated Document Serving}: \texttt{GET /files/\{entity\}/\{id\}/\{field\}} enforces token verification. Direct URL guessing of Aadhaar, PAN, licence, or RC documents is prevented.
    \item \textbf{Magic-Byte Sniffing}: Uploads are validated against genuine binary signatures (PDF, JPEG, PNG, WEBP). Disguised executables (such as \texttt{payload.exe} renamed to \texttt{doc.pdf}) are rejected.
    \item \textbf{Brute-Force Protection}: Login failures are tracked on composite \texttt{(IP + Username)} keys. 5 consecutive failures lock the source for 15 minutes without blocking other corporate users.
    \item \textbf{Server-Side Token Revocation}: Logout places the token's \texttt{jti} in an in-memory denylist, invalidating the session across REST, WebSocket, and file download routes.
\end{itemize}

\subsection{Mobile Client Security Controls}

\begin{diagrambox}{Mobile Security Controls}
1. CA-Level Certificate Pinning (Pinned to Let's Encrypt CA chain)
2. Hardened OS Storage (EncryptedSharedPreferences / Keychain first_unlock)
3. Proactive + Reactive Session Expiry (Local exp check + 401/403 purge)
4. Root / Jailbreak Detection (Fail-closed SecurityGate block screen)
5. Biometric & Credential App Lock (local_auth, re-locks on background)
6. Native Screen-Capture Protection (FLAG_SECURE / iOS privacy cover)
7. Release Code Hardening (Android R8 Shrinking + Dart Symbol Obfuscation)
8. Cleartext HTTP Blocked & Cloud Backups Disabled
\end{diagrambox}

\begin{itemize}[leftmargin=*]
    \item \textbf{CA-Level Certificate Pinning (\texttt{tls\_pinning.dart})}:
    Pins HTTPS traffic to the Let's Encrypt intermediate (\texttt{YR1}) and root (\texttt{ISRG Root YR}) Certificate Authority chain, surviving 60-day leaf renewals while blocking proxy interception (Burp Suite, mitmproxy).
    \item \textbf{Hardened Storage Wrapper (\texttt{secure\_store.dart})}:
    Android uses \texttt{EncryptedSharedPreferences} (AES-256-GCM in KeyStore/StrongBox). iOS uses Keychain with \texttt{kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly}. OS cloud backups and ADB data transfers are disabled (\texttt{data\_extraction\_rules.xml}).
    \item \textbf{Device Integrity \& Root Blocking (\texttt{device\_integrity.dart})}:
    Detects root binaries, test-keys, and Magisk/Jailbreak hooks via \texttt{safe\_device} / RootBeer. Compromised devices are halted at a fail-closed, un-dismissible "Security Check Failed" screen.
    \item \textbf{Biometric Session Gate (\texttt{app\_lock.dart})}:
    Prompts for Biometric (Fingerprint/Face ID) or device PIN unlock on startup and whenever returning from background.
    \item \textbf{Native Screen-Capture Protection}:
    Android sets \texttt{FLAG\_SECURE} in \texttt{MainActivity.kt}. iOS adds a privacy window overlay in \texttt{SceneDelegate.swift} upon \texttt{sceneWillResignActive}.
\end{itemize}

\subsection{Real-World Threat Scenarios \& Mitigations}

\begin{itemize}[leftmargin=*]
    \item \textbf{Scenario A: Unauthenticated Document Scraping (CRITICAL-1)}
    \begin{itemize}
        \item \textit{Threat}: An external actor attempts URL enumeration against \texttt{/files/driver/15/aadhaar} to bulk-download confidential identity cards.
        \item \textit{Mitigation}: The backend requires an active JWT token. Unauthenticated requests receive \texttt{401 Unauthorized}, and every document access writes to \texttt{audit\_logs}.
    \end{itemize}

    \item \textbf{Scenario B: Executable Disguised as Profile Photo (HIGH-1)}
    \begin{itemize}
        \item \textit{Threat}: An attacker uploads an executable binary renamed to \texttt{avatar.jpg}.
        \item \textit{Mitigation}: The server inspects the raw binary magic bytes. Non-image headers are rejected immediately regardless of the client-supplied file extension.
    \end{itemize}

    \item \textbf{Scenario C: Rogue CA / Proxy Interception (MOB-1)}
    \begin{itemize}
        \item \textit{Threat}: A compromised root certificate or corporate inspection proxy attempts a Man-in-the-Middle attack on mobile traffic.
        \item \textit{Mitigation}: The mobile client trusts only the embedded Let's Encrypt CA chain. Requests through untrusted proxies fail the TLS handshake before request data is transmitted.
    \end{itemize}

    \item \textbf{Scenario D: Shared Office IP Brute-Force Lockout (MEDIUM-3)}
    \begin{itemize}
        \item \textit{Threat}: An attacker makes 5 failed login attempts against an administrator's email. Under simple IP lockouts, all 50+ staff in the office sharing that public IP would be locked out.
        \item \textit{Mitigation}: Lockouts are keyed on \texttt{(IP + Username)}. Only the attacker's specific composite connection is throttled; legitimate users continue working normally.
    \end{itemize}
\end{itemize}

\subsection{Architectural Limitations \& Future Roadmap}
\begin{enumerate}[leftmargin=*]
    \item \textbf{In-Memory State Multi-Worker Scaling}:
    The token revocation denylist, login lockout counters, and WebSocket broadcast manager operate in-process within Python memory. When scaling horizontally across multiple server instances, provision a centralized Redis cache to manage token denylists and Pub/Sub broadcasts.
    
    \item \textbf{Short-Lived Signed Document URLs}:
    Files are currently served through token-guarded API endpoints. Future iterations will introduce short-lived HMAC pre-signed URLs (such as S3 or Cloud Storage presigned GET) for offloaded direct file streaming.
    
    \item \textbf{Multi-Factor Authentication (MFA)}:
    Implement TOTP (Time-Based One-Time Password) second-factor authentication for administrative accounts on the web client.
\end{enumerate}
