\section{Executive Summary \& System Architecture}

Canaan ERP is a mission-critical, trip-centric logistics enterprise system designed specifically for container transport operations (Chennai port logistics). The system manages the entire operational lifecycle: booking intake, vehicle/driver assignment, on-road tracking, trip-sheet reconciliation, accounts verification, and GST-compliant invoice generation --- alongside fleet compliance, maintenance, tyre lifecycle management, fuel logging, staff/driver attendance, finance, and per-truck P\&L analytics.

The system is deployed as a unified ecosystem:

\begin{enumerate}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Backend REST API + WebSocket Server}: FastAPI (Python) serving 205 endpoints across 21 domain routers with token-guarded authentication, optimistic locking, and real-time broadcast.
  \item \textbf{Relational Database}: MySQL ($\sim$40 tables, LONGBLOB document storage, automated startup migrations).
  \item \textbf{Web \& Desktop Frontend}: Next.js 16 (App Router) + React 19 Single Page Application, also packageable as an Electron desktop application.
  \item \textbf{Mobile Companion App}: Flutter (iOS \& Android) Admin client providing real-time operational monitoring, offline caching, and biometric device security.
\end{enumerate}

\subsection{Enforcement Mechanisms}
\begin{enumerate}[leftmargin=1.4em,itemsep=4pt]
  \item \textbf{Backend Route Guards}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Every API router requires a valid JWT via \texttt{Depends(get\_current\_user)}.
    \item Sensitive endpoints use \texttt{require\_roles(...)} dependencies (e.g.\ \texttt{/finance} and \texttt{/pl-summary} enforce \texttt{require\_roles("Accounts", "Admin")}).
    \item Destructive operations (such as \texttt{DELETE /trips/\{id\}}) verify admin status or valid temporary edit tokens.
  \end{itemize}
  \item \textbf{Frontend Route Guards}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item \texttt{Sidebar.tsx} and \texttt{nav-config.ts} maintain a strict \texttt{ROLE\_HREFS} map. Unauthorized menu items are pruned from the DOM.
    \item Upon authentication, users lacking dashboard privileges are redirected directly to their designated workspace (e.g., Yard Supervisor $\rightarrow$ \texttt{/trips/sheet-collection}).
  \end{itemize}
  \item \textbf{Mobile Client Gate}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item The mobile application strictly admits the \texttt{Admin} role. Non-admin logins are rejected client-side before token persistence, and rejected server-side on all admin endpoints.
  \end{itemize}
\end{enumerate}

\subsection{Architectural Data Relationship Rules}
\begin{enumerate}[leftmargin=1.4em,itemsep=4pt]
  \item \textbf{Trip as the Core Decoupled Hub}: The \texttt{Trip} model holds hard foreign keys to \texttt{Customer}, but references \texttt{driver\_id} and \texttt{vehicle\_id} using stable string codes (\texttt{CGI-D001}, \texttt{CGI-T001}). This ensures historical trip manifests remain immutable even if a driver or truck profile is modified or archived.
  \item \textbf{Automatic Diesel Synchronization}: When a \texttt{TripSheet} is saved, the backend parses its embedded \texttt{diesel\_entries} JSON and automatically creates or updates corresponding entries in the \texttt{FuelLog} table tagged with \texttt{source = "Trip Sheet-\{id\}"}.
  \item \textbf{Polymorphic Transactions}: \texttt{CompensationTransaction} and \texttt{LeaveRequest} support both staff and driver entities via polymorphic keys (\texttt{person\_type} + \texttt{person\_id}, \texttt{category} + \texttt{applicant\_id}).
\end{enumerate}

\subsubsection{Stage 1: Trip Booking \& Assignment (Commercial Manager)}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item \textbf{Container Number Format}: Rigorous regex validation requiring exactly 4 letters followed by 7 digits (\texttt{\^{}[A-Z]\{4\}[0-9]\{7\}\$}), enforced on up to 3 container slots.
  \item \textbf{"Self" (CGI) Operational Rules}: When billing party is "Self (CGI)", payment is locked to Credit, freight invoice type defaults to Transport Memo (no GST), driver advances are hidden, and CHA is locked to "CGI".
  \item \textbf{Baseline Mileage}: Baseline distance (\texttt{approx\_km}) is captured at booking time to serve as the reference for downstream variance checks.
  \item \textbf{Lift-On/Off Rules}: Auto-populated from customer rate tables for standard containers; manual for Open/Shifting; forced to 0 for Coastal.
\end{itemize}

\subsubsection{Stage 2: Trip Execution}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item Status progresses through: \texttt{Assigned} $\rightarrow$ \texttt{Started} $\rightarrow$ \texttt{Loaded} $\rightarrow$ \texttt{On-Transit} $\rightarrow$ \texttt{Reached} $\rightarrow$ \texttt{Unloaded} $\rightarrow$ \texttt{Completed}.
  \item Live status changes trigger instant WebSocket broadcasts across all connected dispatch screens.
\end{itemize}

\subsubsection{Stage 3: Trip Sheet Collection (Yard Supervisor)}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item Yard supervisor collects physical trip sheets upon truck return.
  \item Validates actual cash advances issued to drivers against system booking records.
  \item Records \texttt{ts\_received\_date} and flags missing sheets if uncollected within 24 hours.
\end{itemize}

\subsubsection{Stage 4: Trip Sheet Reconciliation (Docs Team)}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item Docs team enters start/end odometers, cargo weight, toll expenses, port pass, mamool, and diesel receipts.
  \item \textbf{$\pm$10\% KM Variance Alert}: If actual odometer distance differs from \texttt{approx\_km} by more than 10\%, a mandatory remark popup blocks saving until an operational explanation is entered.
  \item \textbf{Diesel Re-sync}: Fuel station receipts replicate directly to the vehicle's fuel maintenance log.
  \item \textbf{Flag for Re-Checking}: Docs can flag ambiguous sheets, preserving draft status without forwarding to accounts.
\end{itemize}

\subsubsection{Stage 5: Accounts Verification (Accounts Team)}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item Accounts reviews freight income, verified driver expenses, and net profit margins.
  \item \textbf{Approval (Tick)}: Locks reconciliation and enables invoice generation.
  \item \textbf{Rejection (Cross)}: Rejection reason is recorded; trip status shifts to \texttt{rejected} with an explanatory banner displayed on the Docs dashboard. Docs must correct data or initiate an Edit Approval request.
\end{itemize}

\subsubsection{Stage 6: Invoice \& LR Consignment Generation (Accounts Team)}
\begin{itemize}[leftmargin=1.2em,itemsep=3pt]
  \item \textbf{Automatic Document Determination}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item \textit{Self (CGI)} $\rightarrow$ \textbf{Transport Memo} (Freight + Halt only; no GST).
    \item \textit{Customer + GTA Registered} $\rightarrow$ \textbf{Bill of Supply} (Freight charges under RCM; no forward GST).
    \item \textit{Customer + Non-GTA} $\rightarrow$ \textbf{Tax Invoice} (Standard forward-charge GST applied).
  \end{itemize}
  \item \textbf{Sequential Numbering}: Thread-safe running sequence per type:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Transport Memo: \texttt{CGI\{FY\}/TM\{nnnn\}}
    \item Bill of Supply: \texttt{CGI\{FY\}/BS\{nnnn\}}
    \item Tax Invoice: \texttt{CGI\{FY\}/T\{nnnn\}}
  \end{itemize}
  \item \textbf{Immutable Dates}: Invoice dates are locked to the current operational date (IST) to prevent backdating.
  \item \textbf{LR Generation}: Automated generation of standardized A4 Lorry Receipts (Consignment Notes) via client-side PDF synthesis.
\end{itemize}

\subsection{Edit \& Delete Approval Protocol}
To prevent unauthorized tampering with closed records, modifying sensitive data (Customers, Vendors, Bookings, Trip Sheets, Closed Trips) requires an \textbf{Edit Approval Request}:
\begin{enumerate}[leftmargin=1.4em,itemsep=3pt]
  \item Requester submits change justification via \texttt{POST /edit-approvals}.
  \item Admin reviews request in \texttt{/attendance/edit-approvals}.
  \item Upon approval, the backend issues an approval token granting a strict \textbf{1-hour modification window} (\texttt{expires\_at}), after which edits automatically lock.
\end{enumerate}

\subsection{Automated Compliance Expiry Warning Engine}
Fleet compliance documents are continuously evaluated against proactive threshold alerts:
\begin{itemize}[leftmargin=1.2em,itemsep=2pt]
  \item \textbf{Fitness Certificate (FC)}: 30 days notice
  \item \textbf{National / Local Permits}: 10 days notice
  \item \textbf{Road Tax}: 10 days notice
  \item \textbf{PUC / Insurance}: 7 days notice
\end{itemize}
Alerts surface immediately on Dashboard stat widgets and trigger notifications across administrative clients.

\section{Real-Time Synchronization \& Data Consistency}

To ensure dispatchers, accounts, and field staff maintain consistent operational state, the platform implements a \textbf{Persist $\rightarrow$ Broadcast $\rightarrow$ Refetch} consistency pattern.

\begin{lstlisting}[style=asciiart]
Client Action (POST / PUT / PATCH / DELETE)
                 |
                 v
     FastAPI Backend Router (DB Commit)
                 |
                 v
     Realtime Broadcast Middleware
                 |
                 v
     WebSocket Broadcast (`/ws`) --> "data_changed" { resource: "trips" }
                 |
                 v
     Frontend Clients (`useAutoRefresh`)
                 |
                 v
     Debounced REST Re-fetch (300ms) --> UI State Updated
\end{lstlisting}

\subsection{Real-Time Pipeline Guarantees}
\begin{enumerate}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Zero Sensitive Payload Over WebSockets}: The WebSocket channel emits only lightweight resource change notifications (e.g.\ \texttt{\{"event": "data\_changed", "resource": "trips"\}}). No business data or personal details travel over the socket frame.
  \item \textbf{Authenticated Sockets}: \texttt{/ws?token=<jwt>} validates token signature, expiry, and revocation denylists upon connection. Sockets automatically close (\texttt{code 4001}) if a token expires mid-session.
  \item \textbf{Debounced Throttling}: Server-side broadcast debouncing (250ms) and client-side hook debouncing (300ms) prevent refetch storms during bulk updates.
  \item \textbf{Graceful Polling Degradation}: In environments without persistent WebSocket proxying (e.g., shared cPanel hosting), \texttt{useAutoRefresh} seamlessly falls back to 60-second polling and focus-triggered refreshes.
\end{enumerate}

\section{Full-Stack Security Architecture \& Hardening}

Both Web and Mobile platforms enforce defense-in-depth security controls designed to safeguard logistics data, financial ledgers, and identity documents.

\subsection{Web \& Backend Security Controls}
\begin{lstlisting}[style=asciiart]
+-----------------------------------------------------------------------------+
|                       BACKEND SECURITY CONTROLS                             |
+-----------------------------------------------------------------------------+
| 1. JWT HS256 Token Auth (12-hour expiry, unique `jti`, fail-closed secret)   |
| 2. Server-Side Token Revocation (Instant `jti` denylist on logout)          |
| 3. IP + Username Lockout (5 failed attempts -> 15 min lock; Admin reset)    |
| 4. Authenticated Document Access (Token-guarded `/files/...`, audit-logged) |
| 5. Magic-Byte Upload Sniffing (File signature validation; 25 MB cap)        |
| 6. Append-Only Tamper-Evident Audit Trail (`audit_logs` table)              |
| 7. Constant-Time Admin Authentication (`secrets.compare_digest`)            |
| 8. Hardened Security Headers (CSP, X-Frame-Options: DENY, HSTS opt-in)      |
| 9. Safe Error Hygiene (Generic client errors, server-only stack traces)     |
+-----------------------------------------------------------------------------+
\end{lstlisting}

\begin{enumerate}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{Authenticated Document Serving}: \texttt{GET /files/\{entity\}/\{id\}/\{field\}} enforces token authentication (via \texttt{Authorization} header or \texttt{?token=} query param). Direct URL enumeration of Aadhaar, PAN, driving licences, or vehicle RC documents is blocked.
  \item \textbf{Magic-Byte Content Sniffing}: Uploaded files are validated against genuine binary signatures (PDF, JPEG, PNG, WEBP). Disguised executables (e.g., \texttt{payload.exe} renamed to \texttt{doc.pdf}) are rejected. Non-image files are served with \texttt{Content-Disposition: attachment} and \texttt{Content-Security-Policy: sandbox}.
  \item \textbf{Brute-Force Protection}: Login attempts are tracked against composite \texttt{(IP + Username)} keys. 5 consecutive failures lock the specific source for 15 minutes without impacting the user logging in from legitimate corporate IPs.
  \item \textbf{Server-Side Token Revocation}: Logging out instantly places the token's \texttt{jti} into an in-memory denylist, invalidating the session across REST, WebSocket, and file download routes.
\end{enumerate}

\subsection{Mobile Client Security Controls}
\begin{lstlisting}[style=asciiart]
+-----------------------------------------------------------------------------+
|                       MOBILE SECURITY CONTROLS                              |
+-----------------------------------------------------------------------------+
| 1. CA-Level Certificate Pinning (Pinned to Let's Encrypt CA chain)          |
| 2. Hardened OS Storage (EncryptedSharedPreferences / Keychain first_unlock) |
| 3. Proactive + Reactive Session Expiry (Local exp check + 401/403 purge)    |
| 4. Root / Jailbreak Detection (Fail-closed `SecurityGate` block screen)     |
| 5. Biometric & Credential App Lock (`local_auth`, re-locks on background)    |
| 6. Native Screen-Capture Protection (`FLAG_SECURE` / iOS privacy cover)     |
| 7. Release Code Hardening (Android R8 Shrinking + Dart Symbol Obfuscation)  |
| 8. Cleartext HTTP Blocked & Cloud Backups Disabled                          |
+-----------------------------------------------------------------------------+
\end{lstlisting}

\begin{enumerate}[leftmargin=1.4em,itemsep=3pt]
  \item \textbf{CA-Level Certificate Pinning (\texttt{lib/core/security/tls\_pinning.dart})}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Pins requests to the Let's Encrypt intermediate (\texttt{YR1}) and root (\texttt{ISRG Root YR}) Certificate Authority chain.
    \item Survives standard 60-day leaf certificate renewals while blocking proxy interception (Burp Suite, mitmproxy, rogue corporate CAs).
  \end{itemize}
  \item \textbf{Hardened Storage Wrapper (\texttt{lib/core/security/secure\_store.dart})}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Android: \texttt{EncryptedSharedPreferences} backed by AES-256-GCM and Android Keystore / StrongBox.
    \item iOS: Keychain configured with \texttt{kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly}.
    \item OS Cloud Backups and ADB device-to-device transfers are strictly disabled (\texttt{data\_extraction\_rules.xml}).
  \end{itemize}
  \item \textbf{Device Integrity \& Root Blocking (\texttt{lib/core/security/device\_integrity.dart})}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Evaluates root binaries, test-keys, Magisk/Jailbreak hooks via \texttt{safe\_device} / RootBeer.
    \item Compromised devices are halted at a fail-closed, un-dismissible "Security Check Failed" screen.
  \end{itemize}
  \item \textbf{Biometric Session Gate (\texttt{lib/core/security/app\_lock.dart})}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Prompts for Biometric (Fingerprint/Face ID) or device PIN unlock on launch and whenever the application returns from the background.
  \end{itemize}
  \item \textbf{Native Screen-Capture Protection}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Android: \texttt{FLAG\_SECURE} enabled in \texttt{MainActivity.kt} to prevent screenshots, screen recording, and app-switcher task previews.
    \item iOS: Native privacy overlay applied over the window in \texttt{SceneDelegate.swift} upon \texttt{sceneWillResignActive}.
  \end{itemize}
\end{enumerate}

\subsection{Real-World Threat Scenarios \& Resolutions}

\begin{infobox}[title={Scenario A: Unauthenticated Document Scraping (CRITICAL-1)}]
\textbf{Threat}: An external actor guesses the sequential file URL \texttt{/files/driver/15/aadhaar} to bulk-download confidential identity cards.\\[3pt]
\textbf{Mitigation}: The backend requires an active JWT token. Unauthenticated requests receive \texttt{401 Unauthorized}, and every access event writes to \texttt{audit\_logs}.
\end{infobox}

\begin{infobox}[title={Scenario B: Executable Disguised as Profile Photo (HIGH-1)}]
\textbf{Threat}: An attacker uploads \texttt{exploit.exe} renamed to \texttt{avatar.jpg}.\\[3pt]
\textbf{Mitigation}: The server sniffs the file's raw binary magic bytes. Non-image headers are rejected immediately regardless of file extension.
\end{infobox}

\begin{infobox}[title={Scenario C: Rogue CA / Proxy Interception (MOB-1)}]
\textbf{Threat}: A compromised root certificate or corporate proxy attempts a Man-in-the-Middle attack on mobile traffic.\\[3pt]
\textbf{Mitigation}: The mobile client trusts only the embedded Canaan Certificate Authority chain. Requests through untrusted proxies fail the TLS handshake before any payload is sent.
\end{infobox}

\begin{infobox}[title={Scenario D: Shared Office IP Brute-Force Lockout (MEDIUM-3)}]
\textbf{Threat}: An attacker makes 5 failed attempts against an administrator's email. Under simple IP lockouts, all 50+ staff in the office sharing that public IP would be locked out.\\[3pt]
\textbf{Mitigation}: Lockouts are keyed on \texttt{(IP + Username)}. Only the attacker's specific connection is throttled; legitimate users continue working.
\end{infobox}

\subsection{Architectural Limitations \& Future Roadmap}
\begin{enumerate}[leftmargin=1.4em,itemsep=4pt]
  \item \textbf{In-Memory State Multi-Worker Scaling}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item The token revocation denylist, login lockout counters, and WebSocket broadcast manager currently operate in-process within Python memory.
    \item \textit{Roadmap}: Provision a Redis instance to back token denylists and Pub/Sub broadcasts when horizontally scaling the backend to multi-instance clusters.
  \end{itemize}
  \item \textbf{Short-Lived Signed Document URLs}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item Files are currently served via token-guarded routes.
    \item \textit{Roadmap}: Implement short-lived HMAC pre-signed URLs (e.g., S3/Cloud Storage presigned GET) for offloaded direct file streaming.
  \end{itemize}
  \item \textbf{Multi-Factor Authentication (MFA)}:
  \begin{itemize}[leftmargin=1.2em,itemsep=2pt]
    \item \textit{Roadmap}: Implement TOTP (Time-Based One-Time Password) second-factor authentication for administrative accounts on the web client.
  \end{itemize}
\end{enumerate}
